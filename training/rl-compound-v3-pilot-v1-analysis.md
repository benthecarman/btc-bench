# Interpretation of the RLVR pilot

The small RL run improved tool-based transfer, but it did not beat the
additional-SFT control on that set. Additional SFT improved transfer in
both interfaces. RL preserved development performance better. Neither
method produced a broad chat improvement.

This result supports expanding training coverage before increasing RL
steps on this 14-question pool. It does not establish that SFT is generally
better than RL. The test is small, uses one seed, and evaluates questions
we have already observed.

## Results that matter

| Fixed final model | Transfer chat | Transfer submit | Human write chat | Human write submit |
|---|---:|---:|---:|---:|
| Parent checkpoint 144 | 35/48 | 36/48 | 34/120 | 33/120 |
| RL, 32 updates | 33/48 | 41/48 | 33/120 | 32/120 |
| Additional SFT, 32 updates | 38/48 | 43/48 | 32/120 | 35/120 |

RL transfer submit gains six questions and loses one relative to the
parent. Its chat result gains two and loses four. Additional SFT gains
ten and loses three in submit, and gains seven and loses four in chat.
On the older development set, RL scores 39/48 chat and 40/48 submit;
additional SFT scores 37/48 and 38/48. The parent scores 39/48 in both.

Human-style write scores remain low. The changes are small and include
regressions. Tree scores remain low too: parent 3/40 chat and 5/40 submit,
RL 3/40 and 5/40, and additional SFT 4/40 and 4/40. A large claim about
general Bitcoin Script ability would not follow from these results.

All 1,024 new evaluation generations finished normally. Chat finishes with
`stop` and submit finishes with `tool_calls`; none reaches the context limit.
All fixture hashes and expected completion counts match. The benchmark
uses the same uncapped generation protocol as the parent runs.

## Was there an RL learning signal?

Yes. The training-only probe sampled eight answers for each of 48 questions.
Fourteen groups had both successes and failures. The pilot trains on those
14 questions, with no evaluation questions included.

During the actual 32 RL updates, 13 groups had mixed rewards and 19 did not.
All 256 completions finished within the trainer's 4,096-token budget. The
run produced 205 correct samples. The initial probe's success rate, weighted
by the actual training question counts, was 57.8%; the training run's sample
success rate was 80.1%. These are different sampled answers, with later
answers generated by an updated model. This is a training diagnostic, not
an evaluation gain.

Loss, gradient norms, and KL values are finite. Both arms complete exactly
32 optimizer updates. The SFT control uses the exact 256 question instances
sampled by RL, replacing each generated answer with the verified reference.
All 256 control target-mask audits pass without truncation.

Training takes about 10:50 for RL and 2:19 for SFT. This excludes model load,
probe generation, merging, and evaluation. The comparison matches question
counts, answer presentations, optimizer updates, and the listed optimization
settings; it does not match token count or GPU time. The existing environments
also differ in PyTorch version: 2.13.0 for RL and 2.14.0+cu130 for SFT. Their
Transformers, TRL, PEFT, Datasets, and Accelerate versions match.

## Intermediate expressions

All 48 reference controls pass. Model policy and Miniscript expressions are
parsed as written, with no syntax repair, in Segwit v0 context. All 288
candidate traces in this check have recognized expression markers.

| Model/interface | Equivalent policy | Equivalent Miniscript | Correct final script | Correct final with invalid Miniscript |
|---|---:|---:|---:|---:|
| Parent chat | 42/48 | 31/48 | 35/48 | 4 |
| Parent submit | 42/48 | 33/48 | 36/48 | 5 |
| RL chat | 44/48 | 30/48 | 33/48 | 3 |
| RL submit | 47/48 | 37/48 | 41/48 | 4 |
| SFT chat | 43/48 | 32/48 | 38/48 | 6 |
| SFT submit | 45/48 | 36/48 | 43/48 | 7 |

RL's tool-interface policy interpretation improves, but construction errors
remain. Both methods sometimes output a correct script with invalid
Miniscript in the preceding explanation. Final-script reward does not
require that intermediate expression to be valid. Intermediate checks do
not change the existing final-answer scores.

Three examples show the distinction:

- Question 001: both methods fix an invalid wrapper in the parent chat answer.
- Question 020: SFT produces a correct final script with the required 48-block
  delay, but its intermediate Miniscript remains invalid. RL still fails.
- Question 018: RL introduces a chat regression. Its policy includes a
  288-block delay, but its Miniscript and final script omit it. The parent
  and SFT chat answers are correct.

See [the complete spot checks](rl-compound-v3-pilot-v1-spot-check.md).

## Next step

Expand the training questions across the failure families in human-style
requests, while retaining chat examples and replay. Keep another independent
evaluation set out of curriculum design. The narrow 14-question pool was
suitable for this pilot, but it is a weak basis for a longer training run.

For another RL comparison, include chat-format rollouts and verify their
answer extraction against the benchmark first. Measure reward variation
again on the expanded training pool. Keep the additional-SFT control and
the intermediate checks. If valid policy and Miniscript are requirements of
the answer, state that contract explicitly and test a reward that checks
them as a separate experiment.

The current verifier checks Miniscript semantics and its supported script
forms. Decoder rejection does not independently establish invalidity of all
possible Bitcoin Script programs. This remains separate from testing signed
transactions with real witnesses.
